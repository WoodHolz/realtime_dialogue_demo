## 验证：背调场景下的动态 Prompt 话题控制

目标：在“电话背调”场景下，验证**两方面**——  
1. **前置 prompt 能多长、多细**，是否可以把 AI 严格约束在某一类背调问题上；  
2. **过程中修改“控制信号”**（system prompt / 软 prompt / 上下文重写），是否真的能改变 AI 的**话题走向、深度和收尾方式**。

这里把“控制信号”拆成三条路径：

- **路径 A：重启 Session 加载新 System Prompt**（FinishSession → StartSession）  
  用于验证：前置 prompt 上限、多细粒度规则、以及“通过重启 session 切换 prompt”对对话话题（阶段）的影响。
- **路径 B：同一 Session 内热更新上下文（511 ConversationUpdate）**  
  用于验证：不重启 session，仅通过“改写上下文中的某条消息文本（question_id / reply_id）”能否**强制换话题或纠正错误记忆**。
- **路径 C：同一 Session 内“软 Prompt 更新”（510 ConversationCreate 写入规则）**  
  用于验证：不重启 session，通过**向上下文追加一条“规则更新/背调专员指令”消息**来约束后续对话（更贴近“热更新 prompt 控制对话”，但它本质是上下文注入，而非 StartSession 的 system_role/speaking_style 热更新）。

本文件以 **电话背调：HR 打电话给候选人前同事/前上司（证明人）** 为例，设计一套可执行的验证流程。

- AI 扮演：**专业、友好的背调专员**（第三方背调公司）。  
- 人类扮演：**证明人**（候选人的前同事或前上司）。

## 背调对话阶段与话题切换点

### 四个核心阶段

为方便控制话题，将背调拆成 4 个阶段（类似“场景分轨”）：

1. **阶段 1：开场与身份确认**  
   - 内容：问候、说明来电身份和目的、确认证明人与候选人的关系、确认是否方便接听。  
   - 验证：AI 不应直接进入具体背调问题，只做开场和关系确认。
2. **阶段 2：基本任职信息核实**  
   - 内容：候选人在贵公司的入职/离职时间、职位名称、是否全职正式员工、汇报对象、工作地点等。  
   - 验证：AI 的问题围绕“硬信息核实”，不提前进入工作表现评价。
3. **阶段 3：工作表现与合作情况**  
   - 内容：主要负责的工作内容、完成情况、优点与改进点，与同事合作情况等。  
   - 验证：AI 提问聚焦在**表现类问题**，不反复追问已经确认的时间/职位等信息。
4. **阶段 4：风险类问题与收尾**  
   - 内容：是否存在违纪/劳动争议、是否涉及竞业协议、离职原因、是否愿意再次共事、总结与感谢告别。  
   - 验证：AI 能切换到**风险/总体评价 + 收尾话术**，在收到“时间不多”等信号时主动收尾。

### 每个阶段中的“话题切换/打断”测试点

在实际测试时，推荐在每个阶段预留 1–2 个“操作者动作”：

- 指示 AI **立刻切到下一阶段话题**（例如从“任职信息”直接跳到“工作表现”）。  
- 指示 AI **中止当前线索**，改问一个新的话题（如从表现类问题切到风险问题）。  
- 指示 AI **提前收尾**（如证明人表示时间有限或多次说“简单说一下就好”）。

## 验证流程总览（电话背调场景）

| 阶段 | 你在 `/voice` 页面做什么 | 应用的 Prompt（动态切换） | 预期现象（验证点） |
|------|---------------------------|---------------------------|--------------------|
| 1. 开场与身份确认 | Mode 选 **e2e**，Stage 选 **introduction**，Start 后用中文简单介绍自己是第三方背调公司 | 使用 **Prompt A（开场与关系确认）** | AI 只做问候、说明来电身份、确认是否方便通话、核实与候选人的关系，不进入任职/表现问题 |
| 2. 任职信息核实 | 在对方确认方便接听后，点 **Apply Prompt** 切到 Prompt B | 使用 **Prompt B（任职信息核实）** | 下一句 AI 问题应围绕入职/离职时间、职位、是否全职等硬信息，不问评价类问题 |
| 3. 工作表现与合作情况 | 证明人回答完基本信息后，再点 **Apply Prompt** 切到 Prompt C | 使用 **Prompt C（工作表现与合作情况）** | AI 提问应切换为“职责/成果/合作”等表现类问题，不再回到时间/职位等已确认信息 |
| 4. 风险类问题与收尾 | 在表现类问题聊了 2–3 轮后，点 **Apply Prompt** 切到 Prompt D | 使用 **Prompt D（风险问题与收尾）** | AI 提问转向风险与总体评价，在听到“时间不多”等信号后能尽快总结并致谢收尾 |

**核心验证**：  
- 阶段 1→2：同一轮对话内，仅通过「过程中改 prompt + 重启 session」，AI 是否从“开场/关系确认”变为“只问任职硬信息”。  
- 阶段 2→3：再改一次 prompt，是否从“任职信息”变为“工作表现与合作”。  
- 阶段 3→4：继续改 prompt，是否从“表现类问题”切到“风险与收尾”，并在需要时提前结束本轮背调。

**补充验证（同一 Session 内热更新上下文）**：  
在不重启 session 的前提下，拿到本轮的 `question_id` 或 `reply_id`，用 511 把对应消息文本改写成“强约束/纠错/聚焦指令”，看下一轮 AI 是否按新的话题要求进行提问。

## 建议的 Prompt 文案（复制到 /voice 页面）

下面所有 System Role / Speaking Style 默认为**中文**；如未来要支持英文，可在同一段下附加英文翻译说明（见文末“未来扩展到英文的预留”）。

### Prompt A — 开场与关系确认（阶段 1 用）

**System Role (`system_role`)：**

```text
你是一名来自第三方背景调查公司的专业背调专员，现在正在电话联系候选人的前同事或前上司，进行工作背景核实。

规则：
- 本阶段只做：问候、说明来电身份和背调目的、确认对方是否方便接听、核实对方与候选人的关系。
- 一次只问一个问题，语速适中，语气礼貌、友好但保持专业。
- 如果对方表示时间有限或有顾虑，优先安抚和解释用途，而不是立刻进入细节提问。
- 暂时不要询问候选人的任职时间、工作表现或离职原因。
```

**Speaking Style (`speaking_style`)：**  
`礼貌、专业、节奏慢一点，重点解释清楚身份和来电目的。`

---

### Prompt B — 任职信息核实（阶段 2 用）

**System Role (`system_role`)：**

```text
你是一名第三方背景调查公司的背调专员，目前已经完成开场和关系确认，进入“任职信息核实”阶段。

规则：
- 只询问候选人在对方公司的基本任职信息，例如：
  - 入职时间、离职时间（大致年月即可）；
  - 是否为全职正式员工，还是实习/外包；
  - 在职期间的岗位名称、所在部门、工作地点；
  - 主要的汇报对象（直属上级的大致职级或岗位）。
- 一次只问一个问题，可以根据前一题的回答做简单澄清或确认。
- 不要问工作表现、优缺点、合作情况、离职原因等评价类问题。
```

**Speaking Style (`speaking_style`)：**  
`条理清晰、问题简洁，听上去像在对表核实信息，不夹带评价。`

---

### Prompt C — 工作表现与合作情况（阶段 3 用）

**System Role (`system_role`)：**

```text
你是一名第三方背景调查公司的背调专员，目前已经核实完候选人的任职时间和岗位信息，进入“工作表现与合作情况”阶段。

规则：
- 围绕候选人的日常工作内容和表现展开提问，例如：
  - 主要负责哪些工作、承担哪些具体职责；
  - 在这些工作中做得比较好的地方、能想到的代表性成果；
  - 需要改进的地方，或者在工作中遇到的困难和不足；
  - 与同事、跨部门合作时的沟通与配合情况。
- 如果对方回答比较笼统，可以在同一主题上追问 1 次，帮助对方举例说明，但不要一次堆很多问题。
- 尽量避免重复询问已经核实过的任职时间、职位等“硬信息”，除非是为了澄清矛盾信息。
```

**Speaking Style (`speaking_style`)：**  
`真诚、耐心、以开放式问题为主，鼓励对方举例，但保持客观专业。`

---

### Prompt D — 风险问题与收尾（阶段 4 用）

**System Role (`system_role`)：**

```text
你是一名第三方背景调查公司的背调专员，目前已经了解候选人的工作内容和表现，进入“风险类问题与收尾”阶段。

规则：
- 重点询问以下内容：
  - 在职期间是否出现过严重违纪、违反公司制度或劳动争议仲裁等情况；
  - 候选人是否签署过竞业限制协议，大致的限制方向（不需要敏感细节）；
  - 对候选人离职原因的大致了解（例如个人发展、家庭原因、组织调整等）；
  - 如果未来有合适机会，是否愿意考虑再次与候选人共事。
- 语气要更加委婉，提前提示“接下来有几项稍微敏感一点的问题”，并尊重对方不方便回答的边界。
- 如果对方多次提到“时间不多”“简单说一下就好”等，请尽快进入总结和致谢，不要再开启新的话题。
- 收尾时，对对方的配合表示感谢，不要做任何评价性承诺。
```

**Speaking Style (`speaking_style`)：**  
`语气柔和、慎重，用词尽量中性，注意控制问题数量并自然收尾。`

## Path A：重启 Session 切换 System Prompt（按阶段切换话题）

### 操作步骤（示例脚本）

1. 打开 `http://localhost:7998/voice`，Mode 选 **e2e**，Stage 选 **introduction**。  
2. 点击 **Start**，允许麦克风。说一句类似的话术，例如：  
   > “您好，我们是第三方背景调查公司，方便占用您几分钟时间，核实一下前同事 XXX 的工作情况吗？”  
3. 确保当前 `system_role` / `speaking_style` 填写为 **Prompt A**，观察 AI 的第一句回复：  
   - 预期是问候 + 简要说明来电身份/目的 + 确认是否方便通话 + 核实与候选人的关系。  
4. 在对话**不中断（不点 Stop）**的前提下，当证明人已经确认“方便接听，并且是前同事/前上司”后：  
   - 将 `system_role` / `speaking_style` 换成 **Prompt B**；  
   - 点击 **Apply Prompt**，等待 log 中出现 `Session restarted`。  
5. 继续用一句简短的话响应，例如重复候选人名字，制造一个自然过渡。  
   - 预期：AI 的下一句问题应立刻切到“入职/离职时间、职位、是否全职”等任职信息核实，不再重复开场话术。  
6. 在任职信息问答 2–3 轮后，再次把 prompt 切到 **Prompt C**，点击 **Apply Prompt**：  
   - 预期：AI 的提问从“时间/职位”等硬信息切换为“主要负责什么工作、表现如何、合作情况”等表现类问题。  
7. 表现类问题进行几轮后，再切换到 **Prompt D** 并 Apply：  
   - 预期：AI 不再详细追问日常工作，而是集中问“是否有违纪或劳动争议、是否有竞业、离职原因、是否愿意再次共事”等风险和总体评价问题。  
   - 如果证明人暗示时间有限，AI 应能在 1–2 个问题后自然进入总结与感谢。  

通过上述操作，可以验证：  
- 使用**不同阶段的长 prompt**，AI 是否能在每一段中只问对应类型的问题；  
- 在中途切换 prompt + 重启 session 后，下一句提问的**话题是否马上切换**，且不会长时间停留在旧话题。

## Path B：511 ConversationUpdate — 在同一 Session 内强制换话题/纠正记忆

目的：验证“**不一定必须靠重启 session 和 system prompt**，也可以通过**改写上下文**来影响后续对话”，重点看**强制换话题**与**纠正错误记忆**是否生效。

### 推荐用法 1：改写用户问题/指令以强制换话题

1. 正常按 Path A 流程进行到 **阶段 2（任职信息）**。此时模型可能还在围绕“入职时间/职位”追问。  
2. 在 `/voice` 页面里，找到 “ConversationUpdate 511” 面板：  
   - Target 选 **last question_id（用户问题）**；  
   - 在 **New text** 中改写为一条更强的指令，例如：

```text
请你接下来只询问候选人在工作表现、合作态度和优缺点方面的问题，不要再问任职时间、职位或汇报对象等基础信息。
```

3. 点击 **Apply Context Update**（不重启 session）。  
4. 继续对话（例如简单回答一句“好的”或补充一两句说明），观察下一轮 AI 提问：  
   - 预期：新的问题应切换到“工作表现/合作情况”等话题，并在后续几轮中不再回到“任职时间/职位”这类已经核实过的信息。

### 推荐用法 2：纠正模型对事实的记忆（改写 reply_id）

1. 在表现或风险阶段，有意制造一个“模型记忆错误”的场景，例如：  
   - 证明人原话是：“他离职主要是个人职业发展原因。”  
   - AI 在总结时误说成：“他因为绩效问题离职。”  
2. 在 511 面板里，将 Target 设为 **last reply_id（模型回复）**，把 **New text** 改写为“模型应该记住的版本”，例如：

```text
（更正）证明人说明候选人离职主要是个人职业规划和发展原因，与绩效或违纪无关；在职期间没有发生严重违反公司制度或劳动争议仲裁。
```

3. 应用 511 后，继续问一两个追问问题或进入总结，观察 AI：  
   - 预期：后续的提问和总结不再假设“绩效问题”或“违纪”，而是沿用更正后的事实表述。

### Path B 的观察点

- 511 更新后的**下一轮提问是否立刻体现新的话题约束**。  
- 后续多轮对话中，模型是否会**再次回到被禁止的话题**或旧的错误记忆。

## Path C：510 ConversationCreate — 软 Prompt 更新下的话题切换

目的：在不重启 session 的前提下，把“新的背调规则”写入上下文，让后续对话明显更受控，尤其是**风险阶段切换**和**提前收尾**。

### 规则更新示例：从表现切到风险

1. 正常对话，已经在**阶段 3（工作表现）**聊了几轮。  
2. 在 `/voice` 页面中，找到 “Apply Prompt (in-session)” / 510 面板。  
3. 在 `system_role` / `speaking_style` 输入框中填入一段规则更新，例如：

```text
规则更新：从现在开始，请优先询问与风险相关的话题，例如是否有违纪、劳动争议、竞业限制以及对离职原因的了解；除非对方主动提及，否则不要继续追问日常工作表现和具体项目细节。
```

4. 点击 **Apply Prompt (in-session)**，页面 log 会显示 `Soft prompt applied (510 context injection)`。  
5. 继续顺着上一轮话题简单回答一句，然后等待 AI 下一句提问：  
   - 预期：问题内容自动转向“是否有违纪/劳动争议、是否有竞业、离职原因”等风险类话题。

### 规则更新示例：提前收尾

1. 在任何阶段，如果证明人表示“时间不多”“简单说一下就好”，可以通过 510 写入一条收尾规则，例如：

```text
规则更新：如果对方表示时间有限或多次提到“简单说一下就好”，请在 1–2 个问题内尽快进入总结和致谢，不要再开启新的话题或深入追问细节。
```

2. 应用 510 后，继续对话（可以简单说一句“理解，谢谢您”），观察模型：  
   - 预期：AI 在接下来的 1–2 轮中，会主动开始总结、确认是否还有补充，并尽快致谢结束通话。

### Path C 的观察点

- 与 Path A 相比，510 属于“**同一 session 内的软 prompt 更新**”，不需要重启。  
- 验证重点：  
  - 规则注入后，后续提问是否明显遵守新的话题和收尾策略；  
  - 是否仍会被此前的对话惯性（例如一直问表现）“拖回原话题”。

## e2e 与 semi e2e 模式下的对比与延迟主观评估

为了同时评估“对话行为一致性”和“延迟体验”，推荐使用**同一套测试脚本**分别在 e2e / semi e2e 下跑一遍。

### 统一对话脚本建议

- 固定一个候选人和证明人背景（例如：互联网公司后端工程师，任职 3 年，后因个人发展离职）。  
- 预先写好证明人可能的典型回答，测试时尽量按脚本回答，减少随机性。  
- Path A/B/C 的关键“话题切换点”和“提前收尾点”在两种模式下保持一致。

### 在 e2e 模式下测试

- 模式：`Mode = e2e`。  
- 完整跑一遍 4 个阶段和 Path A/B/C 的关键步骤。  
- 记录主观感受：  
  - 从你说完话到 AI 开始说话的大致时间；  
  - 在切换 prompt 或注入 510/511 后，下一轮提问是否同样按预期切换话题；  
  - 是否出现明显卡顿或对话中断。

### 在 semi e2e 模式下测试

- 模式：`Mode = semi e2e`。  
- 使用**相同的脚本**和 prompt 切换顺序，人为点击发送文本/播放音频。  
- 重点观察：  
  - 端到端感受的延迟是否比 e2e 明显增加；  
  - 切换 prompt / 注入 510/511 后，对话行为是否与 e2e 一致；  
  - 是否更容易出现“重复老问题”或“话题切换不及时”的情况。

### 延迟体验检查表（主观即可）

- [ ] e2e：在各阶段话题切换后，模型开始说话的延迟大致在 **X 秒以内**，整体可接受。  
- [ ] semi e2e：在相同脚本下，延迟相较 e2e 是否明显增加；如果增加，是否在团队可接受范围内。  
- [ ] 在网络与硬件正常情况下，不出现长时间卡顿或多轮完全无响应。  
- [ ] 在 prompt / 上下文更新后，下一轮提问的行为在两种模式下基本一致。

## 验证清单（背调话题控制视角）

- [ ] **阶段话题边界**：在各阶段的专用 Prompt 下，AI 是否只问该阶段应包含的问题类型（如开场只做介绍与关系确认、不提前问表现/离职）。  
- [ ] **话题切换即时性**：在对话中途切换 Prompt 或注入 510 规则后，下一句是否立即进入新的话题（如从任职信息切到表现，或从表现切到风险）。  
- [ ] **打断与提前收尾控制**：在证明人表达时间有限时，AI 是否能结束当前线索并开始收尾，而不是继续展开新问题。  
- [ ] **上下文更新有效性（511）**：通过改写 question_id/reply_id，能否成功纠正模型记忆或强制换话题，且后续不会再回退到旧话题或错误事实。  
- [ ] **软 Prompt 更新有效性（510）**：通过注入规则更新，后续提问是否明显遵守新话题与收尾策略。  
- [ ] **模式对比与延迟体验**：同一测试脚本在 e2e 与 semi e2e 下，对话行为是否一致，延迟体验是否在可接受范围内。
